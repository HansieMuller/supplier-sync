# Design decisions

This project is original, AI-assisted educational work using fictional data.

1. **Operation row as outbox and state machine.** A separate event bus or workflow framework would obscure the failure cases. One row records intent, due time, lease, budget and completion; attempt rows preserve execution evidence. Every business-side entry point creates intent in the same PostgreSQL transaction.
2. **OSS Sidekiq is transport, not authority.** Lost and duplicate deliveries are expected. PostgreSQL lease recovery repairs the enqueue/consumer loss windows. Tokens fence stale local commits; they cannot prevent an old HTTP call from running. The provider's retained idempotency contract must cover that external effect.
3. **A small custom producer for a real bound.** A Redis Lua LLEN/SADD/LPUSH script writes Sidekiq's JSON protocol atomically. A check followed by an ordinary push would race at capacity. This couples a small method to the pinned Sidekiq protocol; the actual-process smoke is the compatibility gate. Only this application producer may enqueue operation jobs. Stock Sidekiq can requeue its in-flight jobs on interruption; with the supplied two-thread, one-process runner this can temporarily add two messages above the admission limit. The database work limits remain enforced. No paid queue feature is required.
4. **One retry owner.** PostgreSQL schedules bounded attempts; Sidekiq retry is false. This avoids multiplied budgets and hidden retry queues. HTTP has explicit connect/read/write timeouts and zero automatic Net::HTTP retries. Worker exceptions become observable terminal/manual-review outcomes; crashed processes recover via lease expiry. A deployment must alert on sustained dispatcher/job errors.
5. **Catalogue checkpoints, not a whole-feed transaction.** Each validated page and cursor checkpoint commits together. Earlier pages remain if the next page fails. The tiny feed has explicit page/item/cursor limits and active syncs coalesce. An integration requiring a coherent full-catalogue snapshot would need supplier snapshot/version support and staging; that guarantee is not invented here.
6. **Authoritative webhook versions.** Highest version wins, equal must agree. Receipt durability is independent of processing success. Unknown references are manual review rather than guessed linkage, including a webhook preceding acknowledgement recovery. Event IDs cannot be reused with a different signed body.
7. **Reconciliation reports, it does not repair.** Files are hashed streamed evidence snapshots. Their original rows and findings are retained. Strict one-record-per-physical-line CSV keeps provenance and limits understandable; multiline fields are explicitly unsupported. Synchronous processing is acceptable only within the small fixed limits. Findings are per file, so a differently encoded/reordered file is new evidence rather than the same import.
8. **Local security appropriate to the scope.** Generated, untracked secrets; Basic authentication over loopback; Rails CSRF on browser writes; a single scoped signed-webhook exemption; no arbitrary provider/callback URLs. This keeps the demonstration runnable without accounts, while documenting the substantial hardening needed for public hosting.

Manual retry grants another finite budget without changing identity. It is not a way to fix a rejected payload; a deliberately different business order requires a new order, after the ambiguous original has been reviewed. Neither operator retries nor fresh delivery tokens imply exactly-once execution.

The attention list filters only failed/manual-review operations and reads at most 21 rows to display a 20-row page plus continuation. An ID cursor avoids deep offsets; the list is live, so a concurrent completion can remove an exception between clicks. This is a focused review path, not an archive. Webhook detail loads the currently matching local order for explanation and never changes the signed subject or repairs an order.
